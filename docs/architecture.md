# 架构说明

## 三个进程

```
detector.monitor     定期检测、评分、按需回写 Sub2API
detector.server      只读看板 + 受限暂停接口
detector.pricing_tick 倍率变化时重算优先级
```

三者通过 `/var/lib/drool-detector` 下的文件与 SQLite 通信，不共享内存、不共享凭据。web 进程在 systemd 层被 `InaccessiblePaths` 挡住，既看不到私有库，也看不到环境文件。

## 数据流

```
Sub2API 管理 API
      │  ① 账号清单（含分组、类型、模型映射）
      ▼
  accounts 表 ──► 本轮待测队列 runs
      │
      │  ② 用该账号自己的凭据直连上游
      ▼
   模型响应 ──► 判定 ──► runs 落库 ──► public/<id>.json（脱敏）
      │
      │  ③ 算分
      ▼
 priority_routing ──► ④ 回写 Sub2API 优先级（可选）
```

## 目录布局

```
/var/lib/drool-detector/
├── private/
│   ├── state.sqlite3     账号、任务、评分、熔断、成本账本
│   └── worker.lock       进程互斥锁
├── controls/
│   ├── accounts.json     暂停/恢复状态
│   └── prices.json       供货倍率（含分时配置）
├── public/
│   ├── state.json        看板数据源（整体脱敏）
│   └── <run-id>.json    单次检测记录
│   └── <run-id>.html    模型生成的动画
└── worker.lock
```

`private/` 永远不对外。`public/` 是唯一被 web 进程读取的目录，里面已经没有任何凭据。

## 检测契约

### 糖果题

固定一道题，标准答案 21。判定流程：

1. 第一次请求
2. 答错 → 立即结束，本轮判定为不通过（不再追问）
3. 答错以外的失败（超时、HTTP 错误）→ 按预算重试
4. 答对 → 发第二次全新独立请求
5. 第二次也答对 → 通过；第二次答错 → 不通过

「连续」是硬条件：两次答对之间如果有请求失败插进来，不算连续通过。

### SVG 动画题

同一个提示词，要求模型输出完整可独立打开的 HTML。判定只看**是否完整结束并提取到 HTML**，不做视觉质量评分。

模型在动画题上会很慢——高思考等级可能要十几分钟才吐第一个正文字符。所以：

- `idle_seconds` 管"多久没数据算断流"
- `default_seconds` / `drawing_platform_seconds` 管"整次生成最多给多久"

两者是独立的。流一直在动但总时间到了，会被记为**预算截断**而不是断流。

## 错误分类

每个尝试都会带一个 `failure_class`：

| 分类 | 含义 | 影响 |
|---|---|---|
| `upstream` | 真实的上游故障（连不上、HTTP 5xx、断流、提前结束） | 参与熔断判定、计入稳定性 |
| `budget` | 上游一直在返回数据，但客户端预算用完 | 不触发熔断、计入稳定性与成本 |
| `local` | 本地配置错误、进程中断、答案无法核验 | 不计入上游故障 |

熔断条件很窄：**同一项检测连续两次尝试都是 `upstream`，且是两次不同的请求**。这样设计的目的是避免误伤——供应商偶尔抽一下不该被停掉，真正的持续故障才停。

## 评分

四个维度各自归一到 0–100：

| 维度 | 权重（默认） | 计算 |
|---|---|---|
| 智力 | 36% | 最近 N 轮已完成糖果评测的双次通过率 |
| 成本 | 36% | `100 / (1 + 倍率)`，倍率越低分越高 |
| 稳定性 | 18% | 最近 N 轮真实请求的成功率（含重试失败） |
| 速度 | 10% | 首正文延迟与端到端 tok/s 各占一半 |

综合分 → 优先级：`priority = min + round((100 - score) × scale)`

分数越高，优先级数值越小（Sub2API 里数值越小越优先）。缺失数据的供应商永远排在末尾，而不是被当成 0 分。

## 与 Sub2API 的边界

只做两件事，每件都带回读校验：

| 动作 | 接口 | 校验 |
|---|---|---|
| 改优先级 | `PUT /api/v1/admin/accounts/{id}` | 改完重新读取，值不一致就报 `PRIORITY_READBACK_FAILED` |
| 改可调用 | `PUT .../{id}` + `POST .../{id}/schedulable` | 改完校验 `schedulable` 与 `status` 都符合预期 |

`routing.write_priority` 和 `routing.write_callable` 默认都是 `false`——**开箱只算分不改网关**。想让它真的接管路由，明确打开。

额外的保护：

- OAuth 账号达到限额时不会写
- 账号已经退出检测范围时不会写
- 每个平台保留一个未暂停、未限额的兜底入口

## 缓存与请求隔离

每次请求都：

- 生成新的 `X-Client-Request-Id`
- 带 `Cache-Control: no-cache, no-store`
- 不携带任何历史对话
- 系统指令以请求标识开头

这能排除客户端侧和历史上下文造成的影响。**上游内部的缓存无法从外部完全控制**，这一点在页面上也如实写明，不做过度承诺。
